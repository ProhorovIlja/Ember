## Full Ember installation beyond the Windows 4 GB EXE limit (Part 45)

**Why the change:** A Qwen3.5-class GGUF plus native English TTS and RU/EN
ASR can exceed the Windows single PE installer ceiling. Inno Setup 6.5.2+
documents ~4 GB maximum for one executable; its `DiskSpanning=yes`
mode is required for larger payloads. For the COMPLETE first Ember edition,
the source now creates an Inno `Ember-VERSION-Windows-x64.exe` plus
`Ember-VERSION-Windows-x64-N.bin` slices (2,100,000,000-byte
maximum per slice). This is a FULL offline installer if and only if every
part is present; one EXE without the `.bin` files is NOT complete.

**User receives one file per chosen distribution type:**

- `Ember-VERSION-Windows-x64-installer-bundle.zip` — single download
  containing the Setup.exe and all numbered data slices. Extract the
  entire archive into one directory, then run the EXE. No model
  download is required after install.
- `Ember-VERSION-Windows-x64-portable.zip` — single download with
  directly runnable app, all offline engines, LLM, ASR and voice files,
  and their license evidence. Extract and run `Ember.exe`.
- `SHA256SUMS.txt` — SHA-256 of both complete ZIP choices.

The new standard-library-only `tools/installer_bundle.py` validates the
exact Inno executable name and **consecutive** `-1.bin ... -N.bin`
slices (rejecting gaps, unknown extra binaries, links, collisions and
overwrites), writes an uncompressed ZIP64 archive to a private temporary
file and rereads every member to verify complete SHA-256 content.
The tested source is saved separately in the Ember research Drive folder.
A local Python 3 no-network synthetic `--self-test` passed nine
bundling/integrity fixture checks. The committed Git blob SHA
`4c64cccfe4a738c4b7054458879a7e464446e770`
matches the **exact locally executed source**.

`release/ember.iss` uses `DiskSpanning=yes` ONLY when the full
`release/build-complete-offline.ps1` requests `-DiskSpanning`; small
text-only developer CI smoke remains unchanged. Multi-gigabyte
`models/` files are installed via `nocompression` instead of
redundantly using Inno's CPU-intensive LZMA2, with the recursive root
entry explicitly excluding that subtree to prevent duplication.
The builder runs the Inno install/uninstall smoke **with slices present**,
then creates the single installer ZIP, hashes both distribution choices,
removes working copies of the raw EXE/data slices from its OWN temporary
staging folder, refuses unexpected files, and atomically moves the final
three files into the requested output folder.

The installed Ember user's voice/LLM/ASR data is NOT generated by this
source logic. The builder still requires trusted, licensed, real Qwen
LLM + native speech/Whisper weights and runtimes supplied before invoking
the command. The tested bundler fixture did **not** package an actual
multi-gigabyte Inno installer; the current branch has not run Qt/MSVC or
Inno on Windows and does not yet have a ready-to-download Ember Release.

Primary Inno specification:
https://jrsoftware.org/inno-setup/documentation/topic_setup_diskspanning.htm

```powershell
python tools/native_speech_acceptance.py --root D:\EmberComplete --run --model qwen3-tts-0.6b --device cpu --samples 2 --report D:\ember-speech-cpu.json
python tools/native_speech_acceptance.py --root D:\EmberComplete --run --model qwen3-tts-0.6b --device gpu --samples 2 --report D:\ember-speech-gpu.json
python tools/native_speech_acceptance.py --root D:\EmberComplete --run --listen --model qwen3-tts-1.7b --voice serena --device gpu --samples 4
```

The default command verifies an **approved** complete voice manifest, content
hashes and real GGUF header but launches nothing. Only explicit `--run` starts
`engines/speech/speech.exe` with the actual bundled TTS GGUF, the same loopback
host/port and CPU/GPU flags as Ember, and a bounded model-load timeout.
The test rejects occupied or foreign-owned ports and checks the PID before
and after private HTTP probes, disables speech.cpp's update check, sends fixed
non-private English sample sentences and validates returned PCM16 audio.
Optional `--listen` requires `--run` and plays each non-silent verified PCM
sample through the default Windows audio output, synchronously and entirely
in memory using `winsound.SND_MEMORY`. No audio file is created, no cloud
audio service is contacted, and playback time is excluded from HTTP latency.
The listener must personally judge naturalness, pronunciation and prosody;
the script does not claim human approval from an audio signal metric.
Each trial measures first HTTP audio byte, PCM duration and signal quality;
the process is stopped in a `finally` block. Output reports contain only
numeric measurements and model/voice labels, never WAV recordings or user
chat text, and cannot silently overwrite an existing result.

Only the 0.6B or 1.7B TTS model **actually listed in the approved manifest**
can pass. The test does not download a model or approve redistribution.
Passing it is not proof of enjoyable English voice or actual device playback
unless the maintainer explicitly listened, nor of microphone accuracy,
multi-process RTX 4070 VRAM sufficiency,
external network isolation of a third-party executable, or a finished app.
Human blind listening and clean Windows 10 acceptance remain mandatory.


### Native worker trust and readiness, 22 November 2026

The managed `llama-server` and `speech.cpp` processes are now marked Ready
only if all conditions hold: the exact Windows loopback listener still
belongs to the launched process ID; an HTTP 200 `/health` response contains
no more than 4096 bytes; its media type is `application/json`; and the parsed
JSON object contains the literal string `"status":"ok"`. An HTTP 200 with
HTML, malformed JSON or a loading/error status never means Ready. This
matches the documented `/health` protocol of both upstream projects.

Native llama.cpp, whisper.cpp, sherpa-onnx Kokoro, speech.cpp and the explicit
local project test subprocesses now receive an environment with inherited
credential-like variables removed (API keys, tokens, secrets, passwords and
cloud-provider credential prefixes). Windows PATH, SystemRoot and GPU/Vulkan
driver settings are preserved. The one-shot Python offline and comparison
tools use the same credential-removal policy and additionally set
`SPEECH_NO_UPDATE_CHECK=1`, `HF_HUB_OFFLINE=1` and
`TRANSFORMERS_OFFLINE=1`.

These controls reduce accidental exposure to native third-party executables.
They do **not** authenticate downloaded EXE/DLLs, prove GGUF weight integrity,
block every possible outbound socket, isolate the process at the OS level,
secure untrusted arbitrary repositories or replace a disconnected-PC
acceptance test. Opt-in model catalog downloads in the native UI remain
independent of the strict one-shot Python offline acceptance scripts.


### Verified native speech tasks before showing Ready — 22 November 2026

A managed `speech.cpp` process is now considered ready **only after both**
the bounded JSON `GET /health` test and a second PID-verified
`GET /v1/models` request. The model inventory must contain the requested
Qwen3-TTS synthesis and/or Qwen3-ASR recognition task, match the configured
0.6B/1.7B `size_label` and expected `architecture`, and declare the
necessary language support. A requested TTS speaker must appear in the
model's voice metadata with language `en`; native ASR requires both
`en` and `ru`. A mismatch fails closed and stops that managed server;
a temporary inventory HTTP error may be retried within the existing
three-minute startup budget. No automatic download or model substitution
is initiated by this check.

The explicit one-shot `tools/native_speech_acceptance.py --run` also
requires actual `/v1/models` TTS/voice metadata before generating
numeric-only PCM quality-gate samples. The explicit text-first
`tools/offline_acceptance.py --run` likewise checks the documented
`llama.cpp` health JSON and the local process's port identity. They
do not compare acoustic naturalness or prevent native executables from
opening external network connections. The inventory comes from the live
process and must not be confused with a verified GGUF license, trusted
provenance or independent model integrity inspection.

### Local voice inventory and English-only speaker controls

The managed Windows UI now reads `speech.cpp`'s verified
`speech.voices[].name` and `language` model metadata. Only advertised
English speakers are exposed for live switching; unsupported speaker
IDs are rejected while native TTS is Ready. Speakers from recognition
models are never merged into the TTS voice list. Changing a permitted
speaker does not secretly restart or download a model. These measures
do not add any voice weights to the installer or guarantee the claimed
speaker identity sounds natural.

### Portable Windows runtime dependency closure — 22 November 2026

The self-contained installer workflow now runs
`python tools/windows_pe_audit.py --root <complete-payload-folder>`
**before** Inno Setup. This standard-library-only tool reads the native
Windows AMD64 PE import and delay-import tables of every EXE/DLL/PYD/DRV
in the payload without loading or executing those programs. An imported
compiler, Qt, Vulkan or model runtime DLL must be in the root application
directory or alongside its importer unless its name belongs to the explicit
Windows 10 system DLL/API-set list. A missing non-system dependency rejects
the installer preflight instead of silently relying on developer-machine
DLLs. Reparse-point payload paths, broken x64 PE headers and oversized
files are rejected. The Windows development CI also tests synthetic PE
fixtures and checks the deployed Qt application directory.

This detects only **static** imports (including standard PE delay-load).
Runtime `LoadLibrary` calls, plugin-discovered graphics backends, CUDA
driver versions, actual Windows 10 build compatibility, and DLL signature
or license trust remain unverified. A portable package is **not** approved
until its real LLM/ASR/TTS binaries and their dependent DLLs are staged,
hash-verified, license-reviewed, and tested on an independent disconnected
Windows 10 machine. Do not assume that passing on GitHub's Windows Server
2022 runner proves compatibility with every Windows 10 installation.

### Native speech model identity — GGUF metadata preflight (22 November 2026)

A checksum and a filename ending in `.gguf` are insufficient to
establish that a model can provide speech. Before a human-approved
**full stable voice** bundle passes `tools/offline_bundle.py verify
--redistribution-required --require-voice`, Ember now inspects the
metadata written by the pinned upstream `speech.cpp v0.11.2`
Qwen3 converters. The stdlib-only `tools/native_gguf_metadata.py`
reads bounded GGUF headers, typed key/value metadata and the complete
tensor descriptor directory without loading weight payloads or starting any
executable. The reader rejects absent or repeated tensor names, unsupported
GGML types, impossible dimensions, misaligned offsets, overlapping tensor
ranges and truncated tensor data. It uses the exact GGML type-trait
block sizes for F32/F16, Q4_K, Q8_0, IQ and other supported quantizations,
and refuses partial quantized row blocks. Duplicate keys are rejected even
if the key is not otherwise needed by Ember. The
`general.alignment` metadata is validated (default 32 bytes). For the
allowed Qwen3-TTS
0.6B/1.7B aliases, it requires the matching
`general.architecture`, `general.size_label`, task
`speech.task=synthesis`, layout 1, compatible `speech.requires`,
English in `general.languages`, paired `speech.voices`,
`speech.voice_languages`, `speech.voice_genders` and
`speech.voice_descriptions`, and at least one English female speaker. When the
user selects a specific speaker in the manual native TTS acceptance
utility, its identity must already appear as English in the GGUF.

Optional bundled Qwen3-ASR 0.6B/1.7B files must advertise
`speech.task=recognition`, the correct architecture/size/layout and
both RU and EN language tags. Their inclusion is optional because
the release still requires the multilingual local Whisper baseline.
This check is independent of, and complementary to, the later
process-owned `/health` and `/v1/models` readiness checks.

Run `python tools/native_gguf_metadata.py --self-test` to test the
bounded parser with synthetic files. To inspect an owned local
weight, run `python tools/native_gguf_metadata.py --model
models/speech/qwen3-tts-0.6b.gguf --alias qwen3-tts-0.6b --voice vivian`.
Neither command downloads data or executes a model. Tensor descriptors
are read, not tensor content; a malicious padded file can still forge
apparently valid ranges. This structural validation **does not prove**
authentic or complete weights, license suitability, signature trust,
GPU support, network isolation, acoustic quality or inference. A real
offline engine load and audio test remain mandatory release gates.
GGUF tensor layout: https://github.com/ggml-org/ggml/blob/master/docs/gguf.md .
GGML type layouts: https://github.com/ggml-org/ggml/blob/master/src/ggml.c
and https://github.com/ggml-org/ggml/blob/master/src/ggml-common.h .

Converter reference: https://github.com/nyosegawa/speech.cpp/tree/v0.11.2/reference/qwen3-tts
and https://github.com/nyosegawa/speech.cpp/tree/v0.11.2/reference/qwen3-asr

### Runtime gender enforcement for selected English speaker

The stable full-voice package already requires at least one English
female speaker in the approved Qwen3-TTS GGUF. The runtime now also
enforces that the **actually selected** voice has
`language=en` and `gender=female` in the real process-owned
`speech.cpp /v1/models` response. The Settings dropdown displays
only verified English female speakers; an installed checkpoint that
contains both female and male English voices does not cause male
voices to appear in Ember's female voice list. The manual
`tools/native_speech_acceptance.py` rechecks the selected voice
against both GGUF and live inventory metadata before PCM trials.
This does not establish voice naturalness or licence provenance.
